# Conversation history and rewind plan

## Background

The unified browser agent currently keeps its complete transcript only in
`agent.state.messages`. Refreshing the page or recreating the component loses
the conversation. Import proposals are also held separately in React state, so
persisting only rendered chat text would not restore an import session
correctly.

This document proposes ledger-local conversation persistence, history browsing,
and non-destructive rewind for both ledger chat and bill import workflows.

## Goals

- Automatically persist completed conversation turns.
- List, open, rename, archive, and delete past conversations.
- Continue a restored conversation using the current provider configuration.
- Restore transaction proposals, including user edits and pending proposals.
- Restore attachment-backed conversations without relying on browser memory.
- Rewind to a user-message boundary by creating a new branch.
- Record whether a proposal was written to the ledger.
- Prevent silent overwrites when the same conversation is open in multiple
  browser tabs.

## Non-goals

- Undoing transactions that have already been written to the Beancount file.
- Synchronising history between different ledger directories or machines.
- Persisting partial streaming deltas as independently recoverable content.
- Editing historical messages in place.
- Branching from the middle of an assistant response or tool-call sequence.

Ledger rollback is deliberately separate from conversation rewind. A rewound
conversation must never automatically delete entries or write them again.

## Recommended storage

Use Python's built-in SQLite support for metadata and structured state, with
content-addressed files for attachments:

```text
.favai/
├── config.json
├── history.sqlite3
└── attachments/
    └── <sha256>.<extension>
```

SQLite provides atomic updates, migrations, pagination, search, and concurrency
control without adding a runtime dependency. Browser `localStorage` should not
be the authoritative store because it is browser-specific, capacity-limited,
and unsuitable for attachments or reliable concurrent updates.

SQLite journal files and the attachment directory remain ledger-local under the
already ignored `.favai/` directory.

## Data model

The exact SQL can evolve during implementation, but the schema should preserve
the following concepts.

### `sessions`

| Column | Purpose |
| --- | --- |
| `id` | UUID generated by the backend or frontend |
| `title` | Automatically derived from the first user message, user-editable |
| `created_at` / `updated_at` | UTC timestamps |
| `status` | `active`, `archived`, or soft-deleted state |
| `model_api` / `model_name` | Provider metadata for display, never the API key |
| `parent_session_id` | Source session for a rewind branch |
| `fork_message_id` | User message at which the branch was created |
| `revision` | Monotonic optimistic-lock version |
| `confirmed_at` | When an import proposal was written, if applicable |
| `confirmed_count` | Number of entries written by the confirmation action |

### `messages`

| Column | Purpose |
| --- | --- |
| `id` | Stable message ID |
| `session_id` | Owning session |
| `sequence` | Stable transcript order |
| `role` | `user`, `assistant`, or `toolResult` |
| `payload_json` | Validated pi-agent-core `AgentMessage` payload |
| `created_at` | Original message timestamp |

Persist the original agent messages instead of the UI's converted chat message
shape. Tool calls, tool results, reasoning blocks, timestamps, and provider
content must survive a round trip for the agent to continue reliably.

### `session_snapshots`

| Column | Purpose |
| --- | --- |
| `session_id` | Owning session |
| `message_sequence` | Transcript boundary represented by the snapshot |
| `proposal_json` | Current transaction proposal |
| `proposal_dirty` | Whether the user manually edited it |
| `pending_proposal_json` | A newer agent proposal waiting for user choice |
| `context_json` | Import mode and ingest warnings needed by the UI |
| `created_at` | Snapshot time |

Snapshots keep proposal state consistent with a restored or branched transcript.
They should not store a permanent copy of the full account tree; current ledger
data is read again when the conversation continues.

### `attachments`

| Column | Purpose |
| --- | --- |
| `id` | Opaque attachment ID used by messages |
| `sha256` | Content hash for deduplication |
| `filename` / `mime_type` | Display and reconstruction metadata |
| `size` | Enforced size accounting |
| `storage_path` | Backend-controlled relative path |
| `created_at` | Upload time |

Image data must not remain as large base64 strings in message rows. Store an
attachment reference in the persisted payload and rehydrate it when reconstructing
the messages sent to the model. Reference counting or a join table should allow
unreferenced files to be collected safely.

## Backend design

Add focused modules instead of expanding the extension class with storage logic:

```text
src/favai/history.py
src/favai/attachments.py
```

`history.py` owns schema creation and migrations, validation, session CRUD,
atomic state saves, pagination, search, optimistic locking, and branch creation.
`attachments.py` owns size limits, hashing, safe paths, deduplication,
rehydration, and garbage collection.

Fava extension endpoints use single-segment routes, so use endpoints such as:

| Endpoint | Methods | Responsibility |
| --- | --- | --- |
| `sessions` | `GET`, `POST` | Paginated list or create a session |
| `session` | `GET`, `POST` | Load or update session metadata |
| `session_save` | `POST` | Atomically save transcript and current snapshot |
| `session_delete` | `POST` | Archive, soft-delete, or purge a session |
| `session_fork` | `POST` | Create a branch at a valid user-message boundary |
| `attachment` | `POST` | Store an attachment and return its opaque ID |

Session IDs are passed through query parameters or JSON request bodies. All
payloads receive structural and size validation before they are written.

### Optimistic locking

Every state save includes the last observed revision:

```json
{
  "session_id": "...",
  "expected_revision": 12,
  "messages": [],
  "proposal": [],
  "proposal_dirty": true
}
```

The backend commits the complete update transactionally and returns revision
13. A mismatch produces a conflict response; the frontend must not silently
overwrite another tab's changes.

### Schema migrations

Store an explicit schema version and run small, transactional forward migrations
when the database is opened. Failure to initialise history should surface as a
history-specific error without preventing the rest of the Fava extension from
loading or importing transactions.

## Frontend design

Introduce a session controller rather than placing persistence logic directly
inside `UnifiedChat`:

```text
frontend/src/history/
├── types.ts
├── serialization.ts
└── useSession.ts

frontend/src/components/
├── ConversationLayout.tsx
├── SessionSidebar.tsx
├── SessionListItem.tsx
└── HistoryActions.tsx
```

`useSession` owns the current session ID and revision, history loading, session
creation, agent restoration, stable-state saves, proposal snapshots, branching,
and conflict handling. `UnifiedChat` remains responsible for input, attachment
selection, agent interaction, and rendering.

All new user-visible strings must be added to both dictionaries in `i18n.ts`.

## Save lifecycle

Do not write every streaming text delta. Use stable boundaries:

1. Create a session when the first message is submitted.
2. Persist the user message before starting the provider request.
3. Persist the committed transcript when the agent run completes.
4. Save after a proposal tool call changes proposal state.
5. Debounce user proposal edits by roughly 500 to 1000 milliseconds.
6. Save committed state after aborts and provider/tool errors.
7. Treat page-unload saving only as a best-effort fallback.

An interrupted run is restored as interrupted, not presented as a completed
assistant response. The UI should let the user continue with a new message or
retry later.

## Restore lifecycle

When a user opens a session:

1. Abort and detach the currently active agent.
2. Load and validate the persisted session payload.
3. Create a fresh unified agent using the current provider configuration.
4. Restore committed `AgentMessage` objects through a single controlled helper.
5. Restore proposal, dirty, and pending-proposal state from the latest snapshot.
6. Rehydrate attachment references only when required for model context.
7. Subscribe the UI to the restored agent and enable continuation.

Implementation must first confirm the supported pi-agent-core state restoration
API for the pinned version. If it lacks a public helper, isolate the required
state assignment inside the agent factory instead of mutating agent state from
multiple components.

The session records its original model for display, but continuation uses the
current configured model. If they differ, show a non-blocking notice.

## Rewind and branching semantics

Expose **Continue from here** on user messages. It performs a non-destructive
fork:

1. Validate that the selected boundary does not split an assistant tool call
   from its result.
2. Copy the transcript through the selected user-message boundary.
3. Restore the most recent proposal snapshot at or before that boundary.
4. Create a new session with `parent_session_id` and `fork_message_id`.
5. Give it an initial title such as `<original title> · branch`.
6. Open the branch and leave the original conversation unchanged.

The first version only supports user-message boundaries. It does not truncate
the source session or branch from arbitrary assistant/tool blocks. This keeps
tool-call history valid and preserves an audit trail for bill classifications.

## History user interface

Use a left sidebar on larger screens and an overlay sheet on narrow screens.
Group sessions by relative date and display:

- Title and last update time.
- Chat or import indicator.
- Unconfirmed proposal, confirmed import, or interrupted status.
- Branch indicator when applicable.
- Actions for rename, archive, and delete.

The backend list is paginated, initially 30 sessions per page. The initial title
comes from the first user message, truncated to approximately 30 to 40
characters; do not spend an additional LLM request on title generation.

## Privacy, limits, and failure isolation

- Never persist API keys, authorization headers, or complete provider requests.
- Treat BQL results, OCR text, proposals, and attachments as sensitive ledger
  data.
- Create files with user-only permissions where supported.
- Resolve attachment paths solely from backend-generated IDs; reject traversal
  and arbitrary filesystem paths.
- Enforce per-attachment, per-request, and total-history limits.
- Add settings for history enablement, attachment retention, retention period,
  capacity display, and clearing history.
- Default to preserving image originals when exact conversation continuation is
  enabled, and explain that storage is under `.favai/`.
- Ensure history database failures do not block configuration, BQL, or bill
  import endpoints.

## Delivery phases

### Phase 1: reliable text and proposal persistence

- Add SQLite schema, migrations, and session repository.
- Add session CRUD and atomic-save endpoints.
- Round-trip validated agent transcripts.
- Persist and restore proposal, dirty, and pending-proposal state.
- Add automatic stable-boundary saves.
- Add history sidebar, create, open, rename, archive, and delete actions.
- Record import confirmation metadata.

Completion criterion: a text-only chat or import proposal can be refreshed,
opened from history, and continued with its UI state intact.

### Phase 2: attachments, rewind, and concurrency

- Store attachments outside SQLite with hash-based deduplication.
- Externalise image content from persisted messages and rehydrate it safely.
- Add **Continue from here** and branch metadata.
- Restore interrupted-run status.
- Add revision-conflict handling for multiple tabs.
- Add attachment cleanup and storage limits.

Completion criterion: an attachment-backed conversation can be restored and
branched without mutating the source or depending on old browser memory.

### Phase 3: history management

- Add server-side search and improved pagination.
- Add archive/recycle-bin and retention controls.
- Add storage usage and cleanup controls.
- Add history export/import using a versioned portable format.

## Test plan

### Backend

- First database creation and idempotent initialisation.
- Forward schema migrations and migration failure rollback.
- Session create, load, page, rename, archive, and delete.
- Agent message validation and lossless JSON round trips.
- Atomic transcript plus proposal updates.
- Revision conflicts between concurrent writers.
- Branch creation without source mutation.
- Rejection of a branch boundary that splits a tool sequence.
- Proposal snapshot selection at a rewind boundary.
- Attachment deduplication, limits, reference cleanup, and traversal rejection.
- History failures remaining isolated from existing extension endpoints.

### Frontend

- Agent message serialisation and attachment externalisation round trips.
- Correct save timing around complete, abort, and error events.
- Proposal restoration, including manually edited and pending proposals.
- Rewind truncation and snapshot selection.
- Original-model/current-model notice.
- Revision conflict presentation.
- TypeScript build and committed bundle idempotency.

## Acceptance criteria

- Refreshing does not lose a completed conversation or edited proposal.
- A past conversation can be opened and continued with the current provider.
- Attachment-backed sessions remain continuable after a refresh.
- Rewinding creates a branch and never changes the original session.
- Confirmed imports are visibly marked and are never automatically replayed.
- Two browser tabs cannot silently overwrite the same session.
- Interrupted runs are clearly identified as incomplete.
- Invalid or damaged history data cannot corrupt the ledger or disable existing
  import functionality.
- All new UI is available in Chinese and English.
